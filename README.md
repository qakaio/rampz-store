# Rampz Store demo

Rampz Store is a fictional storefront for QA practice. Product orders, payments,
authentication, and the browser-based admin panel are demonstrations only.

See [GUIA-AUTOMACAO-QA.md](./GUIA-AUTOMACAO-QA.md) for the Playwright portfolio
test strategy, existing and recommended scenarios, test data, and scripting
examples.

## Requirements

- Node.js 20 or newer
- No third-party packages are required
- Docker Engine with the Compose plugin is optional for the containerized local run

## Environment

- `PORT` selects the listening port (default `3000`; `0` asks the operating
  system for an available port).
- `HOST` selects the listening interface (default `127.0.0.1`). Docker Compose
  sets it to `0.0.0.0` inside the container; the host port remains bound to
  `127.0.0.1`.
- `NODE_ENV` defaults to `development`. Set it to `test` to enable the
  deterministic server seed reset endpoint. Set it to `production` to serve
  the built files from `dist/`; seed reset is disabled in this mode.
- The demo server binds to `127.0.0.1` and keeps API data in memory. It is not
  a production commerce backend and must not be exposed as one.

## Project structure

- `index.html`, `app.js`, and `styles.css` are the vanilla-JavaScript frontend.
- `catalog.js` is the shared catalog seed used by the API and static storefront.
- `server/` contains the local HTTP server, deterministic in-memory seed, and
  pure business rules.
- `tests/` contains API integration/unit tests; `e2e/` contains Playwright browser tests.
- `scripts/` contains the static production build and OpenAPI validation.
- `openapi.json` documents implemented API endpoints; `404.html` is the
  branded not-found page.
- `.github/workflows/ci.yml` defines the Node.js build and validation pipeline.
- `dist/` is generated by the build and is not source-controlled.

## Run locally

```powershell
npm run dev
```

Open `http://127.0.0.1:3000`. Set `PORT` to use another local port. The server
binds to loopback and serves the static storefront as well as the API utilities.

## Run with Docker Compose

With Docker Engine and the Compose plugin installed, run:

```powershell
docker compose up --build
```

Open `http://127.0.0.1:3000`. The container listens on its internal network
interface while Compose publishes the service only on the host loopback
interface. The container runs as the unprivileged `node` user and includes a
health check. Stop it with `Ctrl+C`; use `docker compose down` to remove the
stopped container. This setup is for local QA only and does not provide
persistent storage or make the demo suitable for public deployment.

## Build and preview

```powershell
npm run build
$env:NODE_ENV = "production"
npm start
```

Open `http://127.0.0.1:3000`. The build copies the static storefront, 404 page,
and OpenAPI document into `dist/`, which is served in production mode. The
demo API remains in-memory and local-only; the static build does not turn it
into a real store or make it suitable for public deployment. `npm run build`
can be run again to refresh the copied files.

GitHub Pages serves the storefront without the Node.js API. On `github.io`
domains, the catalog loads from the shared static seed instead of requesting
the unavailable API endpoints. API-backed checkout coupon and shipping
calculations still require the local demo server.

## API utilities

- `GET /health` and `GET /api/v1/health` report service status.
- `GET /api/v1/categories` returns the seeded categories.
- `GET /api/v1/products` returns the product catalog with optional `q`,
  `category`, `minPrice`, `maxPrice`, `inStock`, `sort`, `page`, and `limit`
  query parameters. The response contains `data` and pagination metadata.
- `GET /api/v1/products/:id` returns one product.
- Product responses include structured, display-ready `specifications` for the seeded catalog; details render these attributes as a labeled specification list.
- The storefront loads its initial categories and full product catalog from these API endpoints. Browser-only admin product edits remain in `localStorage` and are not written back to the server.
- If either catalog request fails or returns invalid data, the storefront shows an explicit catalog error instead of silently using a stale hard-coded catalog.
- `POST /api/v1/coupons/validate` accepts `{ "code": "LAB20", "subtotal": 350, "email": "novo@rampz.test" }` and returns the validated discount or free-shipping benefit. Coupon thresholds and first-paid-order eligibility are checked against the server's in-memory seed.
- `POST /api/v1/shipping/calculate` accepts `{ "cep": "01310-000", "subtotal": 100, "coupon": "FRETEGRATIS" }` (`coupon` is optional) and returns the simulated region, price, delivery days, and `freeShipping` flag. The checkout uses this endpoint when moving from address to shipping and recalculates after coupon changes and before payment.
- `GET /api/v1/openapi.json` serves the OpenAPI 3.1 specification for the implemented API routes.
- `POST /test/reset` and `POST /api/v1/test/reset` restore the deterministic
  in-memory test seed. This operation returns `403` unless `NODE_ENV=test`.

Authentication, cart, order, and administrative API endpoints are not
implemented yet. Coupon validation and shipping quotes are demo-only, use
in-memory seed data, and do not reserve products or place orders. Seed reset
affects only the server's in-memory data; it does not clear the storefront's
browser `localStorage`.

API and static responses include baseline security headers (content-type
sniffing disabled, frame embedding denied, no referrer, and camera/microphone/
geolocation disabled). JSON request bodies are limited to 16 KiB.
Malformed percent-encoding in static paths returns `400`; paths that resolve
outside the project root or to non-public files return a branded HTML `404`.
Unknown `/api/...` routes continue returning JSON `404`. Static serving is
allowlisted to the storefront, its JavaScript/CSS, the OpenAPI document and the
404 page; project configuration and server source files are not served.
Write requests are limited to 60 per minute per client IP and endpoint; excess
requests receive `429` with a `Retry-After` header. Counters are in memory and
reset when the server restarts, so production deployments need a shared limiter
at the edge or in a persistent store.

## End-to-end tests

Install the locked project dependencies and Chromium once:

```powershell
npm ci
npx playwright install chromium
```

Run the isolated browser suite, or open Playwright's UI runner:

```powershell
npm run test:e2e
npm run test:e2e:ui
```

Playwright starts a local test-mode server on `127.0.0.1:4173`, resets its
in-memory API seed before each scenario, and uses a fresh browser context with
cleared local storage. The suite covers catalog, cart, checkout, simulated
payment outcomes, account, cancellation, responsive overflow, and keyboard
search. GitHub Actions runs the same suite on Chromium. HTML reports and traces
are written to ignored `test-results/` and `playwright-report/` directories.

For the static GitHub Pages storefront, run only the browser flows that do not
need the local API:

```powershell
npm run test:e2e:pages
```

This suite defaults to `https://qakaio.github.io/rampz-store/`. Set
`E2E_BASE_URL` to test another deployed static storefront. Checkout shipping
and coupon calculations require the local API and remain covered by
`npm run test:e2e`.

`npm run build` creates the production static files. `npm run check` validates
JavaScript syntax and OpenAPI structure/references. `npm test` runs API
integration tests and isolated unit tests for coupon and shipping rules.
GitHub Actions builds the storefront, runs these checks and tests on Node.js 20
for pushes and pull requests, then uploads the TAP report as a workflow
artifact. The API tests start and stop their own local server processes. No
test data is written to a database or external service.
